## 1. Goal

`ingest` reads a Word file (`.docx`) and a PDF with real text into the same `Document` that stages 2 to 4 read, with hidden text, comments, tracked changes, furniture, undecodable text and scanned pages found and flagged, never removed. Every hostile file ends as a named input error inside its time and memory limits, and `python -m clause_tracer.ingest` reads the Spec 14.5 sample as a PDF that carries the white hidden line.

## 2. Scope

**Where the code starts.** `ingest` reads text, Markdown and pasted text ([stage 2 plan](stage-02-ingest.md)): `read_text_file`, `read_pasted_text` and `split_clauses`, with the limits of Spec 9 in `limits.py`, Lingua in `language.py`, and NUPunkt in `_sentences.py`. It returns a `Document` with no glyphs: `glyphs`, `char_map`, `pages`, `furniture`, `hidden`, `undecodable` and `tracked_changes` are `()`. `core` already holds every shape this stage fills ([system design 3.4](../system-design.md#34-core-shapes-for-stage-1)): `PageBox`, `Page`, `Glyph`, `SourceFile`, `HiddenText`, `TrackedChange`, `InputWarning`, `Document`, `HiddenReason` (nine members), `FileKind` (`PDF`, `WORD`), and the errors `UnreadableFileError`, `ScannedPdfError`, `OldWordFileError` and `EncryptedPdfError`. The last check before drawing in `core` (`draw_check.py`) already reads `Glyph`, `Page` and `char_map`. No PDF or XML library is a dependency yet, and `scripts/check.sh` has no licence check. CI runs on Linux only.

**Hidden text in later modules.** `links` and `privacy` read all of `Document.text`. The notes of stages 2, 3 and 4 each leave it to stage 5 to say whether they skip `Document.hidden` spans (question 3).

### Builds

- The runtime libraries `pypdfium2`, `pikepdf` and `lxml`, each imported in one file of `ingest` only (B4), and the test-only tools (question 9).
- A licence check in `scripts/check.sh`: the runtime group is MIT, BSD or Apache, except `pikepdf` (MPL-2.0), allowed by name (ADR 0007 action item 2, testing strategy section 8).
- Fixture builders, in code, for Word files, PDFs with known glyph positions, and hostile files (testing strategy sections 5 and 8).
- The hostile-file limits: member count, declared and real expanded size, compression ratio, page count, nesting depth, time and memory, each `[Assumption]` until measured (ADR 0007 action item 3, question 11). Parsing runs in a child process with a time and a memory limit (question 1).
- File kind from the bytes: a `.doc` (OLE2) raises `OldWordFileError` whatever its name (question 17).
- One hardened `lxml` parser for every Word part: no entities, no network, no DTD, no huge tree, and any `DOCTYPE` rejected. Relationships marked `External` are never followed.
- The Word reader: paragraphs, runs, tabs, breaks and tables in order; hidden runs through the style cascade; list numbers rebuilt (question 4); comments (question 5); footnotes, headers and footers (question 5); tracked changes read as accepted, each listed with its earlier and new wording and its author, and removed words never in `Document.text` (question 16).
- The PDF reader, through the raw `pypdfium2` API: pages, glyphs with boxes, the canonical text built from glyphs with `char_map`, ligatures (one glyph, two letters), the line-end hyphen kept, duplicate glyphs, furniture (question 13), scanned pages (question 12), undecodable text and its 1-in-20 page warning `[Assumption]`, encrypted files (question 18), and the one coordinate function (question 20).
- The hidden-text checks: low contrast (question 2), tiny font, off the page, invisible render mode, opacity, hidden layers through `pikepdf`, Word hidden runs and comments, zero-width and bidi characters in every kind of input, including text, Markdown and pasted text, and any further Unicode checks the owner chooses (question 6).
- The pdfplumber cross-check as a test only (ADR 0007 action item 4).
- Property tests of invariants 1 and 6 (testing strategy section 5), and a Hypothesis file mutation test on every change.
- The PDF form of the Spec 14.5 sample with the white hidden line in the automatic-renewal clause (Spec 14.5), its golden outline, and the highlight pictures.
- The nightly job: Hypothesis at 2,000 examples and file fuzzing (question 8). The Windows CI job, if the owner chooses stage 5 (question 7).

### M1: Tools, core shapes and fixtures

When this is done, the three runtime libraries are installed and pinned, a licence check runs, `core` holds the new `Document` field and the new `HiddenReason` members, `cli` holds the codec for the child process reply, and code can build the Word, PDF and hostile fixtures that every later milestone tests with.

**Build order.** Build in number order. T10 needs the PDF writer of T3 and the builder of T8.

**Rules for every task of stage 5.**

- Every new shape is written `@dataclass(frozen=True, slots=True, kw_only=True)`.
- A file whose name starts with `_` is internal to `ingest`. `__init__.py` re-exports only the names a task says to export. The file of each library is fixed: `pypdfium2` is imported in `ingest/_pdfium.py` only, `pikepdf` in `ingest/_layers.py` only, `lxml` in `ingest/_xml.py` only. No other non-test file of `src/` imports them (B4).
- `ingest` code is pure (T1): bytes in, `Document` out, no file, clock, network, process or print. Only `__main__.py` reads files and prints. The child process lives in `cli` (question 1).
- Every `ValueError` of a stage 5 helper starts with `ingest: `. Errors for the user are the `InputError` classes of `core`, which carry a code and a context of ids, counts and names, never contract text (I5 to I7).
- Offsets are half-open, count code points and point into `Document.text`.
- A constant that stage 5 sets as an `[Assumption]` lives in `ingest/limits.py` (or `ingest/_thresholds.py` for the hidden-text checks, S5-M5-T1) as `NAME: Final[...] = value`, with a comment line `# [Assumption] <source>: tuned in testing.` The tasks give the name and the value. The implementer never picks a value.
- **Values to confirm.** The expected values in the task text (a span, a text, a count, a reason) are the planner's values, worked out from the research and the rules of the task. The implementer never changes one. If a test fails, the code or the value is wrong: bring it to the owner. Expected values of a whole fixture live in the owner tables (S5-M3-T9, S5-M4-T12, S5-M5-T7, S5-M5-T8), and the owner writes them (Constitution T11). A fixture builder returns what it placed (a character, its position, its size), so a test can compare the reader with the builder and not with a typed number.
- A dev tool (`reportlab`, `PIL`, `pdfplumber`) is imported only in a `tests/` folder or in `scripts/`. The test of S5-M1-T3 checks it.
- While an owner task blocks a task, go on with the tasks that do not depend on it. Do not start the next milestone's branch before the owner merges this one.
- If a task seems to need a design choice, stop and ask the owner. Do not choose. If the build must differ from the task, record it in section 10.

- [x] **S5-M1-T2: The licence check**
  - **Build:** Create `scripts/check_licences.py`, with these names:
    - `ALLOWED: Final[frozenset[str]] = frozenset({"MIT", "MIT License", "BSD-2-Clause", "BSD-3-Clause", "BSD License", "Apache-2.0", "Apache Software License"})`.
    - `NAMED_EXCEPTIONS: Final[Mapping[str, str]] = {"pikepdf": "MPL-2.0", "pillow": "MIT-CMU", "typing-extensions": "PSF-2.0"}`. A named package passes only when its licence text equals the stated one, so a changed licence fails.
    - `def runtime_packages(pyproject: Path) -> tuple[str, ...]`. It reads `[project].dependencies` with `tomllib` and walks `importlib.metadata.distribution(name).requires` for every package, skips a requirement whose marker is false in this environment (`packaging.requirements.Requirement(...).marker.evaluate()`) or that has `extra ==`, and returns the normalised names (lower case, `_` to `-`), sorted, with no duplicate. A package that is not installed raises `SystemExit` with the message `licences: <name> is not installed`.

It returns the `License-Expression` metadata, else the `License` metadata when it is not empty and not longer than 200 characters, else the classifiers that start with `License ::`, with the prefix `License :: OSI Approved :: ` removed, joined by `, `. When all are empty it returns `"unknown"`.

### M2: Limits, file kind and the child process

A file that is too large, too deep, too slow, encrypted or an old Word file ends as a named input error inside its limits, through a child process.

**What the child runs in this milestone.** The child calls one `ingest` function, `read_file(data, *, name)` (S5-M2-T5). In M2 it reads text and Markdown files (as in stage 2), finds the kind of a file from its bytes, raises `OldWordFileError` for an OLE2 file, runs the zip checks and the hardened parser on a Word package, and then stops with a `NotImplementedError("S5-M3")`. A PDF stops with `NotImplementedError("S5-M4")` after the kind check. These two lines are temporary: S5-M3-T8 and S5-M4-T8 replace them. M2 tests only the hostile files that end before those two lines: OLE2, a bad zip, too many members, a false size, an oversize part, a `DOCTYPE`, an entity, deep nesting, a huge text node, and a Word file that is too slow or too greedy to parse. The PDF hostile cases (page count, image bomb, dense text) move to M4 (S5-M4-T11).

**How a test gets a slow or greedy input with no hook in shipped code.** The runner takes its limits as arguments, with the production values as defaults. A test passes a small time limit or memory limit and a real file that is heavy to parse: `big_xml_docx(MAX_XML_PART_BYTES - 1 MiB)` takes about 0.8 s and about 400 MB to parse on the research machine. Production code has no test switch.

**Memory floor.** Importing `clause_tracer.ingest` with `lingua`, `lxml`, `pypdfium2` and `pikepdf` needs about 360 MB of address space (measured 26 Nov 2026 on Linux, Python 3.13). Parsing a part of 32 MiB peaked at about 760 MB in all. So the child limit of 1 GiB fits a part at the cap. Measured again on 26 Nov 2026 with a body of many tiny paragraphs, the worst case: parts of 54 MiB in all fit inside 1 GiB and 60 MiB do not, and `libxml2` reports the lack of memory as an `XMLSyntaxError`, so such a file ends with reason `xml_invalid` and not `memory`. The total cap of 48 MiB stops it first. A limit below about 450 MB fails at import, not in the parse: a test never sets one.

**Rules for M2.** The error for a file that is hostile in structure (not a zip, too many members, a size that lies, a `DOCTYPE`, deep nesting, invalid XML, a missing part) is `UnreadableFileError` with a `reason` in its context. The error for a file that is only too large (a part over the cap, or a total over the cap) is `InputTooLargeError` with the part name and the limit. A reason is a short snake_case word and is part of the contract: tests assert it. A context holds names, counts and limits, never contract text.

### M3: The Word reader

`read_word_file` returns a `Document` whose text is the accepted view as Word draws it, with hidden runs, comments and tracked changes listed, and the side text in `Document.side_text`.

**The model of the text (the planner's rules, P12 in section 6.1).** Every task of M3 follows these rules. They are the decided questions 4, 5, 16 and 21 written as code rules.

- `Document.text` is the body in order, one paragraph for each line, each line ended by `"\n"`. A table row is one line: its cells joined with `"\t"`. A cell that holds more than one paragraph gives them joined with one space. A nested table in a cell is flattened into the cell: its cells joined with `"\t"` and its rows joined with one space.
- A list number is put at the start of its paragraph, followed by exactly one space, whatever `w:suff` says (question 4).
- A run's text is read in order from `w:t` (as it is, no stripping), `w:tab` and `w:ptab` (`"\t"`), `w:br` and `w:cr` of any type (`"\n"`), `w:noBreakHyphen` (`"‑"`), `w:softHyphen` (nothing) and `w:sym` (the character of its `w:char` hex value when the value is from U+0020 to U+D7FF; nothing for any other value, which includes the private-use area, because the symbol-font mapping is a guess). A symbol the app cannot read is never silent (owner, 26 Nov 2026): the document gets the warning `word_symbol_unread` when the body holds a `w:sym` that gives nothing, a `w:sym` whose `w:font` is a symbol font, or a run with text that is not white space whose font is a symbol font. `SYMBOL_FONTS` is `symbol`, `wingdings`, `wingdings 2`, `wingdings 3` and `webdings`, compared in lower case. The characters are still read by the rules above, so a typed tick box can show as a letter. Only the body is checked: comments, notes, headers and footers are a known limit. `w:instrText`, `w:delInstrText` and `w:delText` are never read as text. A field shows its cached result: the runs between `separate` and `end`.
- The accepted view (question 16): the content of `w:del` and `w:moveFrom` is dropped, whatever its child tag. The content of `w:ins` and `w:moveTo` is read. Only the current properties are read: a property is read from the direct child of a `w:rPr`, `w:pPr` or `w:numPr`, never by a search of descendants, so the old values inside `w:rPrChange`, `w:pPrChange` and the like are never read. A paragraph whose mark is deleted (`w:pPr/w:rPr/w:del`) joins the next paragraph with no separator, and its list number is not written. A paragraph with a deleted mark and no text left is dropped with no empty line. A table row marked deleted (`w:trPr/w:del`) is dropped. A table row marked inserted is read.
- Content controls (`w:sdt`), hyperlinks, smart tags, custom XML and `w:fldSimple` are walked through. `mc:AlternateContent` is read once: the `mc:Choice` branch when there is one, else the `mc:Fallback` branch. When the other branch holds different text (compared after joining and stripping), a `HiddenText(span=None, reason=WORD_PART_NEVER_SHOWN, boxes=())` is added. The text of a text box (`w:txbxContent`) is read as its own paragraphs, right after the paragraph that holds the box, and once.
- `w:altChunk` (content imported from another file) is never read, and Word shows it. So a file with an `altChunk` that the walk reaches raises `UnreadableFileError({"reason": "word_alt_chunk"})` (P13, decided 26 Nov 2026). An `altChunk` inside deleted content (`w:del`, `w:moveFrom`, a deleted row) or inside the alternate-content branch that is not read does not show, and raises nothing. An `altChunk` in a comment, note, header or footer raises the same error.
- Side text (comments, notes, headers, footers) is read with the same run rules, with no list numbers and no tracked-change listing, into `Document.side_text`. A hidden run in side text is not located; one `HiddenText(span=None, reason=WORD_HIDDEN_RUN, boxes=())` is added for each side entry that holds one.
- A `HiddenText` for a run has `span` over the run's text in `Document.text` and `boxes == ()`. Two touching spans of one reason merge into one.

**File layout of M3 (P6).** `_word_model.py` (the shared shapes), `_word_styles.py`, `_word_numbering.py`, `_word_body.py` (the walk, the assembler and the changes), `_word_side.py` (comments, notes, headers, footers), `word.py` (the public call).

### M4: The PDF text

`read_pdf_file` returns a `Document` whose text is built from glyphs, with `char_map`, boxes, furniture, undecodable spans and the scanned and encrypted cases handled. The hidden-text findings come in M5: `Document.hidden` is `()` in this milestone.

**The model of the PDF text (the planner's rules, P14 in section 6.1).** Every task of M4 follows these rules. They are the decided questions 12 to 15, 18 and 20 written as code rules.

- **One record for each PDFium character.** `_pdfium.py` (the only `pypdfium2` file) reads one `CharRecord` (`_pdf_model.py`) for each character of the text page, in PDFium's index order, which is the order of the content stream. Everything after that is pure code over `CharRecord`s, tested with made-up records. A `CharRecord` has: `page: int`, `index: int`, `code: int` (from `FPDFText_GetUnicode`), `box: PageBox` (in the shown page, S5-M4-T2), `origin_y: float` (the baseline, in the shown page), `size: float` (the drawn size: `FPDFText_GetFontSize` times the matrix scale `sqrt(abs(a * d - b * c))` of `FPDFText_GetMatrix`), `fill: tuple[int, int, int, int]` (red, green, blue, alpha, from `FPDFText_GetFillColor`), `render_mode: int` (from `FPDFTextObj_GetTextRenderMode` on the object that `FPDFText_GetTextObject` returns, cached for each object), `generated: bool`, `hyphen: bool`, `unicode_error: bool` and `obj: int` (the address of the text object, used only to compare two characters).
- **The text is built for each character from `code`, never from `get_text_range`.** A character with `generated` true gets no glyph: a generated space is written as `" "` with a `None` entry in `char_map`; a generated CR or LF is dropped (the reader writes its own line break, below). A `hyphen` character (PDFium retypes a line-end hyphen to code 2) is written as `"-"` with its real glyph. A character whose code is 0, `0xFFFE`, `0xFFFD` or a control character other than tab is written as `"�"` and counted as undecodable. Any other character is written as its code point (one Python character; an astral code point is one character). A character with `unicode_error` true is written as its code point and counted as undecodable too, because its letters may be wrong.
- **Lines come from baselines.** A line break (`"\n"`, with a `None` entry) is written when the baseline of a character differs from the baseline of the character before by more than `LINE_BREAK_RATIO` times the drawn size of the current character (`LINE_BREAK_RATIO = 0.7`, an `[Assumption]`), so a superscript stays on its line and a short object on a new baseline starts a new line. A page break writes one `"\n"` too. No line break is written at the very start of the text, and none after the last character. The reading order is PDFium's order: columns drawn row by row, a reversed stream and a rotated page are known limits that fixtures record (question 15).
- **A ligature is one glyph.** Consecutive characters of one text object (`obj` equal) whose boxes are equal are one `Glyph`, and every text character of them points to its index in `char_map` (P14: option B of question 14). A line-end hyphen and every other character has its own `Glyph`.
- **One glyph for each real character.** `Document.glyphs` holds the glyphs in text order, `char_map[i]` is the glyph index of `text[i]` or `None`, and `Glyph.page` equals `Glyph.box.page`.
- **The page is the page as shown** (question 20). `Page(number, width, height)` and every `PageBox` are in the shown page: after rotation and inside the bounding box that PDFium gives (`FPDF_GetPageBoundingBox`), top-left origin, PDF points. A character outside that box keeps its box, and is flagged `OFF_PAGE` in M5. A page whose shown width or height is not above 0 raises `UnreadableFileError({"reason": "page_size_invalid", "page": n})`.

**Build order.** Build in number order.

**File layout of M4 (P6).** `_pdf_model.py` (`CharRecord`, `PageFrame`), `_pdf_geometry.py` (the one coordinate function, pure), `_pdfium.py` (all `pypdfium2` calls), `_pdf_text.py` (the canonical text, pure), `_pdf_pages.py` (undecodable, scanned and furniture rules, pure), `pdf.py` (the public call).

Every hostile fixture raises its hidden-text finding, and every innocent look-alike raises none.

**What the research settled (26 Nov 2026).** The check in section 4 ("PDFium and hidden layers") is answered. PDFium returns the text of a layer that is switched off, so the characters are in `Document.text` and a finding has a span. The text object of each character carries a mark named `OC` whose parameter `Name` is the layer's name (measured with `pypdfium2` 5.15.2 on a file written with `pikepdf`: `FPDFPageObj_GetMark`, `FPDFPageObjMark_GetName` gave `OC`, and `FPDFPageObjMark_GetParamStringValue` for the key `Name` gave the layer name). The type of the layer reads as a name that cannot be read as a string, which does not matter. `pikepdf` supplies which names are switched off. S5-M5-T3 builds on this and repeats the measurement as a test.

**The model of the checks (the planner's rules, P17 in section 6.1).**

- A PDF character is hidden by exactly these tests, each a pure function over a `CharRecord` or a bitmap: a drawn size under `TINY_FONT_PT` (`TINY_FONT`); render mode 3 (`INVISIBLE_TEXT`); a box wholly outside the shown page (`OFF_PAGE`); a fill alpha under `OPACITY_LIMIT` (`LOW_CONTRAST`); a rendered contrast spread under `CONTRAST_SPREAD_LIMIT` inside the glyph's box widened by one pixel (`LOW_CONTRAST`); a text object in a layer that is switched off (`HIDDEN_LAYER`). A generated character, a space and a line break are never flagged. Text of 6 to 8 points and a light watermark stay unflagged.
- A `HiddenText` for a PDF run has the `span` over the flagged characters in `Document.text` (a generated space between two flagged characters is inside the span), the `reason`, and `boxes`: one `PageBox` for each line of the run, the union of its glyph boxes. Two touching spans of one reason merge. A character may have more than one reason: it gets one `HiddenText` for each.
- Mistakes fall on the side of more false alarms (question 10). Fixtures lie far from each limit, so a test never depends on a one-level difference.
- Unicode checks apply to the text of every kind of input: text, Markdown, pasted text, Word and PDF (question 6).
