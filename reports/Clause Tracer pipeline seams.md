# Code closes most of each seam

Two of the three seams can be mostly closed by design, and the third can only be shrunk. **The offset chain is mostly killed.** If the AI points at numbered sentences instead of searching freely, and every later step keeps an exact map instead of guessing, each link becomes a lookup that code can test. What stays open is a small set of broken or hostile PDF fonts and drawing bugs. Code can spot these and flag them, but it cannot fix them. **False-Missing replies are minimised, not killed.** No method can prove that a clause is absent. But making "Missing" mean "four separate searches all found nothing" lowers the risk a lot. One published system raised its hit rate from 54% to 88% this way, at low cost ([Ironclad](https://ironcladapp.com/resources/articles/retrieve-then-verify-how-ironclads-ai-matches-playbook-rules-to-long-contracts)). **The AI's free text is mostly killed.** Code can write the label explanations, the Missing text, the unsure questions and the whole message to the other side from templates. The AI keeps four short, fenced jobs: the reasons for a pencilled words label, the two readings of vague wording, the not-covered summaries and clause rewrites. Every guard proposed here is plain code, costs at most about two cents per review, and fits the Constitution. Several guards change what the Spec promises, so eight decisions are left to you. None of this changes the earlier build order. It adds work inside stages 1, 4, 5, 8, 10 and 11, and it moves the message step earlier.

## Three hand-overs where a mistake can slip through

A **seam** is a place where one step hands its work to the next. A mistake made at a seam is hard to see, because each step on its own looks fine. The earlier report found that most of Clause Tracer is already safe. Code picks labels for number and yes/no positions. Code checks every quote. The AI cannot choose which step runs next. The risk that remains sits at three seams. This section explains each one with a small example. The words in the table below are used throughout the report.

| Word | What it means here |
| --- | --- |
| **Offset** | A position in a text, counted in characters from the start. "Characters 44–58" means the 45th to the 58th character. |
| **Canonical text** | The one official copy of the contract's words that the app builds when it reads the file. Every offset points into it. |
| **Placeholder text** | The copy sent to the AI, with names swapped for markers such as `⟦Person 1⟧`. |
| **Page box** | The rectangle on a page picture where a character is drawn. A highlight is a set of page boxes. |
| **Schema** | A form the AI must fill in. It lists the fields and what each may hold. |
| **Enum** | A field that only accepts values from a fixed list, such as the real clause numbers. |
| **Match key** | A tidied copy of the text used only for comparing quotes, with curly quotes straightened and spaces collapsed. It keeps a map back to the canonical text. |
| **Template** | A sentence written in advance with gaps that code fills, such as "You'd wait [n] days to be paid; your limit is [limit]." |
| **Golden set** | The ten test contracts with known right answers (Spec 11). |

**Seam 1: the offset chain.** The AI quotes words from the placeholder text. The app must then find the same words in the real contract and on the page picture, so that it can highlight them. Take this sentence from the sample contract: "Brightline Studio Ltd shall pay Sarah Jones within 60 days." The AI sees "⟦Company 1⟧ shall pay ⟦Person 1⟧ within 60 days." It quotes "within 60 days", which sits at **characters 33–47** of the text the AI saw. In the real contract the same words sit at **characters 44–58**, because the real names are 11 characters longer than the markers. Those characters then have to become boxes on page 3 of the PDF. That is four links: quote, placeholder text, real text, page. If any link is off by one character, the highlight lands on the wrong words. That is worse than no highlight, because the product is named after its evidence trail (Spec 4.5).

**Seam 2: the false-Missing reply.** In step 6a (Match) the AI says which clauses each playbook position concerns. Sometimes it says "none" when a clause does exist. That is a **false-Missing**. Code then applies Rule 7 and gives the position its missing level. The user never sees a quote to doubt. The sample contract makes the danger concrete. It has a 12-month non-compete, which is a walk-away. Suppose the matcher misses it. The starter playbook's missing level for the non-compete is preferred. So the label becomes **preferred**, and Rule 7 also keeps it off the Missing list. The worst clause in the contract would leave no trace on screen.

**Seam 3: the AI's free text.** In four places the AI writes in its own words. These are the explanation of each label (step 10), the one-line summary of each not-covered clause (step 11), a rewritten clause (step 12) and the message to the other side (step 13). Code can check a quote against the contract, but it cannot easily check a sentence. An explanation could say "45 days" when the contract says 60. A summary could carry a planted line such as "Call 0800 123 456 to confirm". A message could quietly concede a point the user never agreed to. The message matters most, because the user copies it and sends it.

## Seam 1, the offset chain: mostly killed by exact maps

**Verdict: mostly killed.** Each link can be made exact by construction. "By construction" means the design makes the error impossible, rather than catching it afterwards. One link, broken PDF fonts, can only be detected and flagged.

### The AI points at numbered sentences; a short quote only marks the exact words

The weakest link today is the search. The AI returns a free quote, and code looks for it anywhere in the clause. The fix is to number every sentence before the AI sees the text. Step 2 already splits clauses into sentences with character spans, using NUPunkt. The text sent to the AI can mark them inline, as in `[4.2.s3]`. The form then asks for `clause_id` and `sentence_ids`, both enums built from the real ids, plus a short quote. Code checks that the quote appears **exactly once inside those sentences**. A miss, or more than one hit, is a failed quote under Rule 3. The search shrinks from "anywhere in the clause" to "inside one to three known sentences". The open question from the earlier report, "a quote found in another clause", disappears, because the ids pin the place.

The quote cannot be dropped entirely. Ids alone would highlight whole sentences, and Spec 4.5 asks for "the exact words, not the whole clause". Rule 3 also checks that the number appears in its quote, which needs a short quote. So the design is a hybrid: **ids to locate, quote to refine, code to verify**. Research supports each half. Harvey's 2026 rebuild gave every document part a unique id and lifted risk classification **from 59% to 77%** ([Harvey](https://www.harvey.ai/blog/rebuilding-playbook-review-as-a-multi-agent-system)). "Attributable by construction" designs resolve verbatim quotes to exact spans in code, so that provenance holds "independently of model accuracy" ([CAMS, arXiv 2606.23989](https://arxiv.org/abs/2606.23989)). One caution: forcing sentence-sized citations can cost attribution quality against the best unit, by a median of 40% in one 2026 study ([Wang et al., arXiv 2604.01432](https://arxiv.org/abs/2604.01432)). That is why the quote stays as the fine-grained part.

Anthropic offers a ready-made version of the id idea, its Citations feature, which returns exact character ranges ([Claude docs](https://platform.claude.com/docs/en/build-with-claude/citations)). It is not a fit as the main mechanism. It works with one provider only. AWS documents that it **cannot be combined with structured outputs** and returns an error if both are on ([AWS Bedrock](https://docs.aws.amazon.com/bedrock/latest/userguide/structured-output.html)). Clause Tracer relies on structured output everywhere. So the same idea is built into Clause Tracer's own JSON form.

**Cost.** One sentence marker costs about 3 to 5 tokens. A 50,000-word contract at about 20 words per sentence has about 2,500 sentences, so roughly **7,500 to 12,500 extra input tokens**. These sit in the part of the prompt that providers cache, so they are paid about once per review: well under one cent at mid-range prices. This is an estimate and should be measured on the sample contract. **Fit.** Ids are a closed form checked where they enter: D4 (treat outside data as untrusted; validate once where it enters) and I16 (ask for structured output and validate it against a schema). Removing the search is I8 (design the error away). Sentence spans are rebuilt from the canonical text, so D2 (make derived data rebuildable) holds.

### Placeholders keep an exact map instead of matching lengths

It is tempting to pad each marker to the same length as the name it replaces, so that offsets never move. Don't. It leaks name lengths to the AI, breaks the readable markers in Spec 4.2, and fails when a name is shorter than its marker. An exact map is simpler. The placeholder text is cut into an ordered list of **segments**. Each segment is either `copy` (the same characters in both texts, shifted by a fixed amount) or `entity` (one marker standing for one name). Escaped characters, such as a `⟦` already in the contract, get their own segment kind, or the map drifts by one character per escape. Mapping a quote back is then a lookup plus one addition, about 40 lines of code. A quote edge that falls inside a marker snaps out to the whole name. In the example, "within 60 days" sits in a `copy` segment shifted by 11, so 33–47 becomes 44–58 with no guessing.

Sentence ids remove most of this link's work. If sentences are numbered on the canonical text, and code makes sure that **no name ever crosses a sentence boundary**, then a sentence id points straight at the real text with no mapping at all. Only the short quote inside the sentence passes through the segment map. One more rule follows: the app shows `canonical[start:end]`, the real slice, rather than the AI's string with names pasted back. What the user reads is then the contract's own words by construction. That is D3 (store each fact once): the quote is a pointer, not a copy. Presidio reports offsets in its output text, so it could feed this map. But the earlier report's choice to keep the map as pure code in `privacy` stands, because Presidio's own mapping is documented as not safe to share between threads ([Presidio sample](https://data-privacy-stack.github.io/presidio/samples/python/pseudonymization/)).

### The canonical text is built from the page's own characters

The last link turns real text into page boxes. It breaks when the text and the drawing disagree. Typical causes are ligatures (the "ﬁ" in "ﬁfteen" is one drawn shape but two letters), line-end hyphens ("pay-" then "ment" on the next line), headers and footers in the middle of a sentence, and flipped page coordinates. The cure is to **build the canonical text from the character records**, never to extract text separately and search it. Every character in the canonical text then carries the number of the drawn shape it came from, or a "generated" flag for spaces and line breaks the app inserted. The browser PDF viewer PDF.js uses the same idea: it records every change it makes to the text and can map any position back ([PDF.js source](https://raw.githubusercontent.com/mozilla/pdf.js/master/web/pdf_find_controller.js)).

The rules that follow are short. A ligature keeps one drawn shape and two canonical letters, both pointing at the same box. A line-end hyphen is **never deleted** from the canonical text. It is only folded away in the match key, and only between two letters, so "2009-2010" keeps its hyphen ([anchorite](https://pypi.org/project/anchorite/)). Headers and footers stay in the canonical text but are skipped in the text sent to the AI. A quote across a page break then becomes two runs of boxes on two pages. These choices follow D1 (keep raw data safe and unchanged) and D2 (make derived data rebuildable from the raw data). Word, text and pasted input are easier. The app lays out those pages itself (ADR 0001), so it knows every box when it draws it. That link is exact by construction.

Two problems remain, and they cannot be designed away. The first is **fonts that cannot be decoded**. Some PDFs have no table that maps drawn shapes to letters, so pdfplumber returns `(cid:x)` instead of text ([pdfplumber docs](https://pdfplumber.dev/errors/cid/)). An open bug in pdfminer.six makes some characters vanish silently while still being drawn ([pdfplumber #1415](https://github.com/jsvine/pdfplumber/issues/1415)). A hostile font can also draw one letter while reporting another. Code can count undecodable characters and treat a page with many of them like a scanned page, which Spec 9 already blocks. A quote that touches undecodable characters can be made unsure, like hidden text under Rule 9. The second is **coordinate bugs**. The earlier design draws page pictures with pypdfium2 and reads boxes with pdfplumber. The two libraries measure pages from different corners. "Most highlighting bugs in practice are coordinate system bugs, not AI bugs," as one 2026 write-up puts it ([Singh](https://medium.com/@harsh100xdev.work/your-ai-read-the-document-can-it-prove-it-b0a8d0c44a23)). There are two ways out. One is to use pypdfium2 for both jobs, which removes the link. That works only if pypdfium2 also exposes the colour and font size that the hidden-text checks need, which was not verified. The other is to keep both libraries and put the one conversion in a single pure function with golden tests on rotated and cropped pages. A cheap extra check compares each page's text from both libraries. A page where they differ by more than a small amount is flagged as "text layer unreliable" before any AI call.

### Tests and a last check before drawing

Each link gets one stated rule that must always hold, called an **invariant**, and a test for it. For example: every canonical character points at a shape or is marked generated; the sentence spans of a clause join up to the whole clause; anonymising then restoring gives back the original; tidying a slice gives the same result as slicing the tidied text. **Hypothesis**, a tool that generates thousands of random test inputs, can try these rules on text with injected ligatures, soft hyphens, curly quotes and random names. A generator script writes test PDFs with known character positions: ligature fonts, two columns, headers and footers, rotated pages, white text and duplicate shapes. A **visual regression test** saves a picture of each highlighted page and fails if it changes. That catches flipped coordinates that number tests built on the same wrong formula would miss. These follow T1 (keep the core pure), T5 (test behaviour at the boundaries) and T6 (test the main promises).

The strongest guard runs in the app as well as in tests. **Right before drawing, code checks again** that the tidied slice of the canonical text equals the tidied quote, and that every character has a box, using a different code path from the one that found it. A bug the tests missed then fails safe instead of drawing the wrong words. Testing and runtime use the same rule.

When a link fails, the outcome should depend on which link failed. A quote that cannot be confirmed is already unsure under Rule 3. A quote that **is** confirmed in the text but cannot be placed on the page is a new case the Spec does not cover. The evidence is real; only its location is lost. The suggestion is to keep the label, wash the whole clause instead, and add a short note. That is a decision for you (see the decisions section). A failed check right before drawing is a bug. It should crash loudly in tests, per I5 (split expected failures from bugs), and show "Check [clause] yourself" in the app.

**What to build**
- Sentence ids on the canonical text in `ingest`, with inline markers in the prompt and `sentence_ids` enums in the 6a and 6b forms.
- The segment map in `privacy`, with `copy`, `entity` and `escape` kinds, and a rule that no name crosses a sentence boundary.
- A canonical-text builder from character records, with a "generated" flag, and a match key with its own position map.
- One pure page-coordinate function, or pypdfium2 for both jobs once its fields are verified.
- An undecodable-font counter and a two-library text comparison per page.
- Invariant tests, generated golden PDFs, a visual regression test and the final check before drawing.

## Seam 2, false-Missing: minimised by four searches that must all fail

**Verdict: minimised.** It cannot be killed. Absence can only be proved by reading every line, and only a person can do that. But the risk can be cut a lot, and code, not the model, can decide when "Missing" is allowed.

### One whole-contract question misses too much

The evidence is consistent. When a strong model was given one rule and a full contract, it **found only 54% of the matches**, and repeat runs sometimes returned different paragraphs ([Ironclad, October 2026](https://ironcladapp.com/resources/articles/retrieve-then-verify-how-ironclads-ai-matches-playbook-rules-to-long-contracts)). On a contract benchmark, models wrongly answered "no related clause" between **1.1% and 7.1%** of the time for large models and up to **30.6%** for small, compressed open models ([ContractEval](https://arxiv.org/html/2508.03080)). These were mid-2025 models, so the pattern matters more than the exact figures. Models find text much less reliably when the clause shares no words with the question. In one test, 11 of 13 models fell below half their short-text score at about 32,000 tokens ([NoLiMa](https://arxiv.org/abs/2502.05167)). A 50,000-word contract is about 65,000 tokens. Noticing that something is absent is a known weak spot: one strong model scored only 69.6% on an absence test ([AbsenceBench](https://arxiv.org/abs/2506.11440)). Asking many questions in one call also loses some of them, and splitting them up helps even a weaker model ([Akinwande et al.](https://arxiv.org/abs/2608.06422)).

### Search both ways, add a keyword net, then ask once more

The strongest measured pattern searches in both directions. Ironclad matched rules to paragraphs, and also paragraphs to rules. Recall of the right paragraphs went **from 62.7% to 88.1%**. After a narrow yes-or-no check of each pair, the system caught **31% more applicable rules** at 3 to 4 times lower cost. A cheap open model then nearly matched a frontier model as the checker (F1 0.776 against 0.788) at about a tenth of the cost per call ([Ironclad](https://ironcladapp.com/resources/articles/retrieve-then-verify-how-ironclads-ai-matches-playbook-rules-to-long-contracts)). Applied to Clause Tracer, that gives four independent nets.

The first is the current **forward pass**: for each position, the whole contract, with clause ids as an enum. The second is a **reverse pass**. Clauses go to the AI in groups of 10 to 20, each with the position list. For every clause the AI must return the positions it concerns, or an explicit empty list. The form requires one answer per clause id, so code can confirm that every clause got a verdict. That is real coverage, not the model's say-so. Missing then needs every relevant clause to be skipped, not one global "no". The third is a **keyword net**, which costs nothing. Each position carries a word list. For the non-compete that might be "compete", "competing", "restrictive covenant", "solicit" and "exclusiv". For positions the user writes, the AI drafts synonyms once per playbook from the topic alone, with no contract text, and the user can edit them. In a clinical study, adding synonyms in this way raised the share of items found from 96% to 99% ([Lopez et al.](https://www.nature.com/articles/s41746-024-01377-1)). The net runs on the match key of the real text, so hidden-text and look-alike-letter tricks cannot hide words. It cannot be steered by planted text, which suits Spec 8.4 ("code picks labels wherever it can"). It misses paraphrase, so it is a floor, not a judge. The fourth is a **targeted pair check**. Where the keyword net or the reverse pass found a candidate but the forward pass did not, code asks one narrow question per (position, clause) pair. The answer is a closed yes or no with a quote, and code checks the quote.

Two more nets are cheap or optional. Step 11 already reads each not-covered clause to summarise it. Its form could also return `may_concern`, a list of position ids, at almost no extra cost. A hit sends the pair to the pair check. That needs a small Spec wording change, because step 11 would then see position topics. **Local embeddings** are a fifth, optional net. They are small models that turn text into numbers so that similar meanings can be found without shared words, such as BGE-M3 (MIT). They run on the computer, but off the shelf they found only about 75% of relevant paragraphs in Ironclad's test, and they add a model download. Build them only if the golden set shows the first four nets leave gaps.

Over-matching is cheap in this design, so the nets should lean towards finding too much. A wrong match goes on to step 6b, which can answer "this clause doesn't state this", and code then drops it. The quote check stops invented evidence. So the small loss of precision from combining nets (Ironclad: 93% against 95%) costs little. Step 6b needs an explicit `not_stated_here` answer for number positions for this to work. A **broken or timed-out reply must never count as "nothing found"**. Spec 6.2 already makes it a retry, then unsure. The code types should keep "empty list" and "failed call" apart, per I4 (always return the same type).

| Net | What it catches | Extra cost per review (estimate) |
| --- | --- | --- |
| Forward pass (today) | Clauses the model sees with the whole contract | none |
| Reverse pass | Clauses with no topic words; every clause gets a verdict | about $0.01–0.02 |
| Keyword net | Clauses that use the topic's words | $0 |
| Pair check where nets disagree | Turns a disagreement into a narrow, checked question | under $0.005 |
| Step 11 `may_concern` | A third look at unmatched clauses | about $0 |
| Local embeddings (optional) | Paraphrase the keywords miss | $0 per call, plus a model download |

Costs assume a 10,000-word contract and a mid-price model at about $0.50 per million input tokens and $3 per million output tokens. They are illustrative. Real figures come from each reply's `usage.cost`. **Fit.** Every answer is a closed form, per D4 (treat outside data as untrusted) and I16 (validate AI output against a schema). Code takes the union and decides. That is Spec 6.1's "the AI only fills forms" and P3 (a fixed pipeline whose steps share no hidden state). Each extra call saves its raw reply, per D8 (save the AI's exact reply), and gets replay tests, per T7 (test everything around the model with a fake).

### Disagreement becomes unsure, with the clause to read

The result should use the labels that already exist. If every net searched and none found anything, the position stays Missing under Rule 7. The Missing item can say how it was searched, for example: "No wording about this was found. The whole contract was searched by keyword and by the AI." It must not say "verified absent", because absence cannot be proved. If a net found a candidate but the pair check said no twice, the position becomes **unsure**, with a reason code such as `MATCH_UNCONFIRMED`. The evidence is the candidate clause, and code can highlight the keyword it found. A draft question: "Read clause 9.2. Does it set a non-compete?" This follows Rule 3's "couldn't confirm, so unsure" logic. A fifth label such as "Possibly missing" is not needed, and it would ripple through the Spec, the copy deck and the prototype.

The silent hole for positions whose missing level is preferred needs a separate fix. Today a false-Missing on the non-compete leaves no trace at all. Options range from listing such positions quietly in the Missing tab to showing them as preferred with "No wording found" as their evidence. Each changes Rule 7, so the choice is yours. Whatever you choose, the guards above should at least run on every position whose missing level is better than its worst level.

### Measure it with built test cases, not just ten contracts

Ten contracts cannot prove a low error rate. With about 80 covered cases and no errors seen, the true rate could still be up to about 4%. This follows the statistician's "rule of three": with n cases and zero errors, the 95% upper limit is about 3 ÷ n. With 300 cases it drops to about 1%. So the golden set needs **built absence cases**. A generator script makes paired versions of each contract: the clause removed with numbering kept; the topic reworded with none of its keywords; the clause moved to a schedule; the clause reached only through a cross-reference ("Sections 7 and 9 survive termination"); and a planted denial line beside a real non-compete. Test sets for absence "must be constructed rather than collected", as one practitioner puts it ([Precision Federal](https://precisionfederal.com/insights/contract-review-ai-when-stakes-are-legal)). Each case should run three times and count as failed if any run fails, because a user only gets one run. The runner should report the raw AI rate, the final rate after the nets, each net's own finds, and a separate count of **dangerous false-Missings**: those where the missing level is better than the right label. These follow T8 (keep a small set of real examples with known good answers).

**What to build**
- A reverse-pass form in `checking`, with one required answer per clause id.
- Keyword lists for the starter positions, and a one-off synonym call per playbook for user positions.
- The pair check, and the `MATCH_UNCONFIRMED` reason code in `core`'s label rules.
- A `not_stated_here` answer in the 6b form for number positions.
- Separate types for "nothing found" and "call failed".
- A per-position record of which nets searched and what each found, so the golden-set runner can count them.
- A generator for paired absence cases, and the false-Missing measures in the golden-set report.

## Seam 3, free text: mostly killed by templates, the rest fenced and scanned

**Verdict: mostly killed.** Code can write the explanation leads, the Missing text, the unsure questions and the message. Four short AI texts remain and are minimised: words-label reasons, the two readings, not-covered summaries and rewrites.

### Code fixes the facts before any sentence is written

The best 2026 evidence on writing from data says two things. Facts, numbers, direction and strength of claim must be fixed by code **before** any prose is written. And letting the AI choose which template gaps to fill still lets facts drift. A hybrid template reproduced only **61.1%** of numbers across runs, "because the LLM still selects which findings and numbers the template renders". Fixing each claim first, and letting the AI write only the connecting words, improved this by **37.4 and 20.5 points** on two tasks, at the lowest token use ([Fan et al., arXiv 2608.25336](https://arxiv.org/abs/2608.25336)). Another study tested what happens when an AI takes back a job from code. Each time, errors returned. Its rule is to "let code own recurring analysis" ([Cheng et al., arXiv 2605.29652](https://arxiv.org/abs/2605.29652)). Even when given only verified facts, top models added unsupported content in **over 70%** of long texts ([PIC-Bench, arXiv 2506.06589](https://arxiv.org/abs/2506.06589)). So asking the AI to "write only from these facts" is not enough.

Templates need not read like a form letter. An AI can draft them once while the app is being built. A person reviews them, and they are saved as code. Nothing generative then runs during a review. A study that did exactly this scored better than the same AI writing live and invented less, on one ordinary computer ([Warczyński et al., arXiv 2502.20609](https://arxiv.org/abs/2502.20609)). The copy deck already writes its leads this way: "You'd wait 60 days to be paid; your limit is 30."

| Output | Code can build it | AI still writes | What full templating would lose |
| --- | --- | --- | --- |
| Explanation lead, number and yes/no labels | Yes, a template per position type, reason and label | nothing | Very little |
| Missing item text | Yes: "The contract doesn't mention [topic]" plus the position's note | nothing | Little |
| Unsure question | Mostly: a template per reason code | Optionally picks one of 2 to 4 code-written questions (an enum) | Some, for unusual wording |
| Reasons for a pencilled words label; two readings when unsure | The frame and the quote | One short reason per reading, no digits | A lot, because the reasoning is the content |
| Not-covered summary (step 11) | Partly: the AI picks a clause type from a list, code shows the heading | Optionally one short sentence | Some, for unusual clauses |
| Rewrite (step 12) | No | A list of small edits that code applies | n/a |
| Message (step 13) | **Yes**: one paragraph per item, per kind and tone | Optionally the connecting words only | Some warmth; the user can edit it (Spec 4.7) |

**The biggest single gain is to template the message.** It is the text the user sends to the other side. Its inputs are already a code-built list: each item's topic, clause number, quote and preferred level. With a template, planted contract text can reach the message only as a quote that code inserts inside quotation marks. It never becomes something the model reads as an instruction. It also costs nothing, works offline and gives the same result every time. This changes Spec 4.7, which says "The AI writes the message", so it is your decision.

### What the AI still writes goes into small, fenced slots

The AI's remaining text goes into short, separate fields of the form. Any choice that can be closed becomes an enum. A field that must not carry facts gets a **pattern**, a rule about which characters are allowed, that bans digits, currency signs, brackets, slashes and colons. The AI then cannot write a number, a placeholder marker, a web address or markup in that field. Code adds any number afterwards from checked values. Each reason must also point at the quote it relies on, by id, so code can show that quote beneath it. If the message keeps an AI option, the form becomes an opening line, one short connecting phrase per item id and a closing line. Code puts each item's fixed sentence and quote after its phrase. The form then forces one paragraph per ticked item.

Providers do not all enforce these rules. On OpenRouter, support for structured output "is determined per endpoint, not just per model", and it can change ([OpenRouter](https://openrouter.ai/docs/features/structured-outputs)). Claude enforces patterns but **not maximum lengths** ([Claude docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). So every rule is checked again in code with Pydantic, and the form sent to the AI is generated from the same Pydantic models, so the two cannot drift. That is D4 (validate outside data, including AI output, once where it enters) and I16 (validate AI output against a schema). Before trusting a pattern, test each chosen provider with a prompt that invites digits, and save the replies as test fixtures.

### Plain-code scans are the gate; small fact-checkers only flag

Every AI text then passes a set of scans. They are pure functions with no cost. They fail any number not found in the step's allowed values, and for steps 10 and 13 any acceptable limit (Spec 6.2). They fail an unknown placeholder, and any name, email, phone or address that Presidio finds and that is not a known placeholder or a defined role. That catches an invented "Dear John". They fail web addresses, phone numbers and "call" or "visit"; law words (Spec 6.2); advice to sign, such as "safe to sign" or "nothing to worry about"; tell-tale injection words such as "ignore", "instruction" or "mark every"; and a label word that differs from the code's label. A real email attack worked exactly through a summary: hidden text made Gemini add a fake security alert with a phone number. The recommended fix was to scan output "for phone numbers, URLs, or urgent security language" ([0din](https://0din.ai/blog/phishing-for-gemini)). In a related study of grounded rewriting, plain-code checks of this kind cut errors per document from 2.48–5.36 to 0.04–0.24 ([Indukuri & Agrawal, arXiv 2607.01457](https://arxiv.org/abs/2607.01457)).

If a scan fails, the AI tries once more, told what failed ("Your text contained a number not in the quotes: 45"). If it fails again, the field falls back to its template. **The failed text is never shown**, and both raw replies are saved, per D8 (save the AI's exact reply).

Small local fact-checkers exist. They are models that score whether a sentence is supported by a source. MiniCheck-Flan-T5-L and FactCG-DeBERTa-L are MIT-licensed and run on an ordinary processor. HHEM-2.1-Open is Apache-2.0 and uses under 600 MB of memory. But they reach only **about 75–77% balanced accuracy** on general text ([LLM-AggreFact](https://llm-aggrefact.github.io/)). On summaries, HHEM caught only about a third of the errors ([HHEM card](https://huggingface.co/vectara/hallucination_evaluation_model)). None has been tested on contracts or on text with placeholders. So they suit a "check this wording" flag, not a gate. A big AI model used as a judge scores in the same band on the same benchmark (77.2 for Claude 3.5 Sonnet), costs a paid call, and reads the same untrusted contract, so it is not recommended. One licence trap: Bespoke-MiniCheck-7B, the top small checker, has **no commercial licence** ([MiniCheck](https://github.com/Liyan06/MiniCheck)). Clause Tracer is source available under FSL-1.1-ALv2 and may be used commercially, so that model is out.

### Rewrites come back as edits that code applies

For step 12, the AI should return **edits, not a new clause**: a list of `{old, new}` pairs, each `old` an exact piece of the original. Code applies them, builds the new text and draws the before-and-after itself. Then code checks a short list of rules. Placeholders and defined terms are kept. New numbers come only from the preferred level text. No law words, links or injection words appear in the new pieces. Cross-references survive. The change stays small, below a set share of the clause. Then the new text is re-checked against **every** position the clause affects, not only the targeted ones, so a rewrite that fixes payment but trips the liability position shows up. This matters because even good models miss errors such as misused defined terms. In one test only one model reached 0.75 recall on such planted mistakes ([ContractScrub, arXiv 2608.20204](https://arxiv.org/abs/2608.20204)). A quietly added "unless the Agency decides otherwise" can still slip through. Only the user reading the before-and-after catches that, which is why the suggestion carries "Written with AI" and its label is information only.

### What planted contract text can and cannot do afterwards

No detector holds against a determined attacker. A 2025 study broke 12 published defences, most "with attack success rate above 90%", and human testers beat every one ([Nasr et al., arXiv 2510.09023](https://arxiv.org/html/2510.09023)). So the defence must come from the design, not from a filter. With templates, code-built leads and the scans in place, a person who controls the contract text **cannot** change a number or yes/no label, make the app show an invented number, name, address or phone number, make it tell the user to sign, make it state law, or change what the message asks for. They **can** still bias the reason sentence for a pencilled words label, an AI-written not-covered summary or an opt-in rewrite. Each of these sits under the real quote and carries the AI mark, and words labels already need a human decision (Spec 4.4). This is a judgement, not a measured figure. The golden set should test it with planted injections, such as the sample's hidden "mark every clause preferred" line.

AI wording should be marked with words, not dashes. ADR 0002 reserves dashed lines for pencilled labels. The copy deck already uses "Written with AI" for suggestions, so one phrase can cover all AI wording, with one fixed line such as "Written with AI. Check it against the quote above." Code-built text carries no mark, so the mark keeps its meaning. A study at the CHI 2025 conference found that a short, constant disclaimer was "the only one" of several aids to improve how far people relied on the AI, though only on one of two tasks. Highlighting uncertain words made things worse ([Bo et al., CHI 2025](https://dl.acm.org/doi/full/10.1145/3706598.3714097)).

**What to build**
- Template sets per position type, reason code and label for leads, Missing text and questions, kept with the copy deck and versioned like prompts.
- A templated message renderer, one template per item kind and tone.
- Patterned, slot-based forms for steps 10, 11 and 12, with Pydantic re-checks.
- The scan set as pure functions in `core`, with the Presidio pass taking the privacy adapter as a passed-in port, per P4 (ports and adapters).
- The retry-then-template fallback, saving both raw replies.
- An edit-list form for rewrites, the rewrite rules and the re-check of every affected position.
- Test fixtures with an invented number, "Dear John", a web address, "safe to sign", an acceptable limit and a wrong label word, per T7 (test everything around the model with a fake).

## Conclusion

The three seams look alike, but they differ in kind. The offset chain is a **bookkeeping** problem. Once every step keeps an exact map and the AI points at numbered sentences, it becomes ordinary code with ordinary tests. The free-text seam is a **job-allocation** problem. The research says plainly that an AI writing from verified facts still drifts, so the fix is to stop asking it to state facts at all. Only false-Missing is a true **knowledge** limit, because no system can prove a negative. That is why it alone gets a "minimised" verdict, and why its release rule deserves your attention more than any prompt wording.

One pattern runs through all three. The cheapest strong guard is usually to **turn an AI answer into a pointer**: a sentence id instead of a free quote, a clause id instead of "none", an item id and a template instead of a paragraph, an exact `old` span instead of a new clause. Pointers can be checked by code, cost almost nothing, and leave a planted instruction nothing to work with. The open question is no longer whether the AI is good enough. It is how much of the remaining wording you want the AI to write at all.
