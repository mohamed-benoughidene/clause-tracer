# Clause Tracer v1: build small, test hard, promise less

Date: 11 Nov 2026

**Summary.** For version 1, build the pipeline on code the developer can review, and prove each promise with a test that fails loudly. Test the AI pipeline with five layers. Four run for free on saved replies, and one runs against the real model on a budget of about **$34 per prompt or model change and about $67 per release** on a Sonnet-class model. Keep the hand-written step runner, frozen standard-library data shapes, `typing.Protocol` ports and the hand-written reply loop. Change five things in the existing architecture report: the storage option, the PDF engine, the HTTP client, the sentence-splitter figures and the pdfplumber claim. Ship Presidio with the `en_core_web_md` model, the ORGANIZATION label switched back on, and a code-first layer in front. Use pywebview as the shell, an engine child process over stdio, PyInstaller one-dir, and Inno Setup. Start with Claude Sonnet 5.5, with GPT-6.1 Terra and DeepSeek V4.1 Flash as comparisons. Do not obfuscate anything, because the source is public. Spend on a trade mark, signed and attested releases, and honest wording about what local encryption can and cannot do. Keep one swappable AI-provider seam so a hosted option stays possible. Much of the product-decision evidence is judgement or seen only in search summaries, and each decision below says so. Nothing in this report is legal advice.

How to read the decision tables. "Verified" means the researcher read the primary source on 11 Nov 2026 or earlier on the date stated. "Judgement" means an inference with no direct study behind it. "Search summary only" means the page was not opened and the detail is unconfirmed.

## Five test layers, and a paid run that costs tens of dollars

The existing plan has five layers, all keyless except one. The research confirms it with changes in tools and targets. The main idea is that live replies cannot be pinned. The chosen model endpoints do not accept `temperature`, and Claude endpoints list no `seed` ([OpenRouter ZDR endpoints API](https://openrouter.ai/api/v1/endpoints/zdr)). Even at temperature 0, output varies because of server-side kernel behaviour ([Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)). Only replay makes an AI-dependent test repeatable.

**Why the layers hold.** Statistics drive the gate design. With zero failures in n independent cases, the 95% upper bound on the failure rate is about 3/n, and the exact bounds are slightly wider ([Cross Validated](https://stats.stackexchange.com/questions/497548/revisiting-the-rule-of-three)). The researcher's arithmetic gives 3.7% at 80 cases, 3.0% at 100 and 1.0% at 300 (one-sided exact). The unit is the case, not the run. Three runs of one case are not three trials, and positions inside one contract are clustered too. Anthropic's own eval guidance found clustered standard errors over three times the naive ones on popular evals ([Anthropic](https://www.anthropic.com/research/statistical-approach-to-model-evals)). So ten contracts are ten clusters. That is why the plan needs small constructed cases for any rate claim. Build them by script from the clean contracts, so the answer key is computed and not typed. Aim for 20 to 50 per kind of case, which gives a per-kind bound of roughly 6 to 15%.

**Gates.** Make hard gates zero-tolerance per case: every planted walk-away found in all three runs, no fabricated quote ever, zero dangerous false-Missings on built cases. Report rates (number accuracy and label match at or above 90%, overall false-Missing) with an exact interval, compared with the last accepted baseline by paired per-case differences. Report "pass^3" (all three runs pass) beside per-run accuracy, because a user gets one run and a case that passes two of three fails one time in three. These gate numbers are the project's own. No published release threshold for false-Missing rates in contract review was found, so do not present them as an industry norm.

**Agent-written tests are the weak spot.** A 2025 survey puts LLM-generated test mutation scores at a peak of 0.546 against 0.690 for human tests ([arXiv 2511.21382](https://arxiv.org/html/2511.21382v1)). Runnable tests are often shallow ([arXiv 2609.05978](https://arxiv.org/html/2609.05978v1)). Coverage and mutation score correlate only weakly to moderately with real-bug detection inside one project ([Zhao and others, arXiv 2607.22880](https://arxiv.org/html/2607.22880v1)). So coverage is a floor. Pair it with mutation on `core`, and keep the red-step discipline that practitioners describe: the failing test must be seen to fail for the right reason ([Fowler site](https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html)). Golden-file regeneration needs a named command, `--update-goldens`, and a change that alters both code and goldens needs a human read of the golden diff. Image baselines must never be updated in the same change as coordinate code without someone looking at the image.

**CI design.** Run the keyless suite on every pull request: lint, types, import rules, unit, integration, property tests on the `ci` profile, fixture-sync checks (every sample has an expected file and the reverse), replay with fail-on-unused, and the visual tests on Linux. Run nightly: Hypothesis at 2,000 examples and the hostile-file fuzzing (see section 3). Run before release: mutmut on `core`. Run the paid suite only by hand or on a labelled change, never on push. Every paid run saves its replies as new fixtures, so the free suite grows with each paid run. Fixtures pass a redaction check before commit: no `Authorization` header, no key pattern, no restored personal data.

**Paid-evaluation budget.** Prices were fetched on 11 Nov 2026 ([ZDR endpoints API](https://openrouter.ai/api/v1/endpoints/zdr), [models API](https://openrouter.ai/api/v1/models)). Figures below are the researcher's estimates, built on 10 golden contracts of about 10,000 words, 10 injected variants, and small constructed cases costing about 20% of a full review, each run three times, caching working.

| Model | 100 small cases plus contracts and variants | Full 300-case set | If each of 300 cases is a full contract |
|---|---|---|---|
| Claude Opus 5.5 | about $67 | about $134 | $504 |
| Claude Sonnet 5.5 or GPT-6.1 Sol | about $34 | about $67 | $252 |
| GPT-6.1 Terra | about $17 | about $34 | $126 |
| Claude Haiku 5.5, GPT-6 Luna or DeepSeek V4.1 Flash | under $5 | under $5 | $13 to $15 |

My recommendation is a two-tier budget. Run the 100-case set on every prompt, model or labelling change (about $34 on Sonnet). Run the full 300-case set before a release or model switch (about $67). A three-model comparison at 300 cases is about $105 per pass, or about $52 at 100. Build the small cases as excerpts, never as full-length variants, because that multiplies cost about fivefold. Cap spend in the runner by summing `usage.cost`, and record cached-token counts, because failed caching raises the cost four to five times on long documents. Setting the cap at about double the table figure for the run type is my judgement, not a researched number. Gaps: the 20% factor, and reasoning-token volume for reasoning-mandatory models, are unknown until the first paid run measures them. Re-query prices before budgeting.

**Where the architecture report is outdated or wrong.** The notes record eight findings. Six change a recommendation.

1. The storage row says the SQLCipher option "relies on a community wheel fork for Windows". That is outdated. The original `sqlcipher3` has shipped self-contained wheels since 0.6.2, and 0.6.5 appeared on 5 Nov 2026 ([sqlcipher3](https://github.com/coleifer/sqlcipher3)).
2. The storage row omits SQLite3 Multiple Ciphers. Its Python wheel is built with secure delete on and memory temp storage ([apsw-sqlite3mc](https://github.com/utelle/apsw-sqlite3mc)).
3. The PDF row calls pypdfium2-alone "unverified". It is now verified against the PDFium headers (above).
4. The report says pdfplumber's `dedupe_chars` "was quadratic until a recent fix". That is wrong. [Issue #1419](https://github.com/jsvine/pdfplumber/issues/1419) is still open and the latest release (0.11.10, 15 Jun 2026) predates it. Issue [#1415](https://github.com/jsvine/pdfplumber/issues/1415), where characters vanish through a pdfminer.six bug, is also open.
5. The report gives pypdfium2 as "8.8 MB". PyPI wheels are 3.6 to 4.5 MB. The 8.8 figure may be an installed size, which is unverified.
6. The report names plain `httpx`. Its last release was 0.28.1 on 6 Dec 2024, and the OpenAI SDK has moved to `httpx2` ([openai-python](https://github.com/openai/openai-python)).
7. NUPunkt's "91.1% precision" differs from the current README, which gives 0.90 to 0.902 precision and 0.782 F1 on legal data. F1 is lower than precision, so recall is the weaker side. About one boundary in five may be missed or wrong on hard legal text, which is why sentence ids must tolerate a missed split.
8. Presidio's default "uses a slim spaCy engine plus GLiNER" is not supported by the code on `main` (see section 3).

The Hamilton cache-key warning in the report is still accurate ([Hamilton caching](https://hamilton.apache.org/concepts/caching/)).

**Encryption design details worth keeping.** Bind each ciphertext to its record by passing `review_id|record_id|schema_version` as associated data, so blobs cannot be swapped. With a key per review, random 96-bit nonces stay far below the 2^32 limit in [NIST SP 800-38D](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-38d.pdf). The `cryptography` AEAD documentation warns that nonce reuse is fatal ([cryptography](https://cryptography.io/en/latest/hazmat/primitives/aead/)). Plain SQLCipher alone does not give per-review shredding, because deleted rows leave old pages until VACUUM, and on SSDs VACUUM does not guarantee physical erasure ([Wei and others, FAST 2011](https://www.usenix.org/legacy/event/fast11/tech/full_papers/Wei.pdf)). Plain per-blob AES-GCM alone leaks metadata such as review counts and timestamps. The hybrid fixes both. The key-wrap API in `cryptography` 50.x was not re-fetched.

**Ship Presidio with `en_core_web_md` and ORGANIZATION on, behind a deterministic layer.** No candidate is good enough alone on organisations and addresses. So typed party details, checksum patterns (bank numbers), company-suffix rules and address rules must carry the promise. NER is a net behind them.

The default-config finding matters. The packaged `default.yaml` still names `en_core_web_lg` and lists ORGANIZATION in `labels_to_ignore` with the comment "Has many false positives". The 23% organisation recall in the vendor benchmark is probably that setting, not spaCy's ceiling. A newer slim engine and GLiNER config exist (merged 12 Apr 2026, [PR #1916](https://github.com/data-privacy-stack/presidio/pull/1916)) but are opt-in and signposted for Presidio v3. So the adapter must ship its own pinned config file, and a test must assert the loaded engine name, model name and recogniser list, because the default is expected to change. A pinned `preshed<3.0.14` was needed in Oct 2026 to keep spaCy model loading working, a live reason to pin the whole stack.

**Measure PII honestly.** Generate contracts from templates with planted entities and offsets computed by code ([presidio-research](https://github.com/data-privacy-stack/presidio-research/blob/main/docs/data_generation.md)). Use Faker and real dictionaries for values, not an LLM, which writes "unnaturally clean" text ([Evaluating PII Detection Models](https://dataprivacystack.org/blog/evaluating-pii-detection-models/)). Inject typos and OCR damage. Score the metric that matches the promise: for each planted value, does any token survive in the placeholder text? That is stricter than span overlap and catches "Ms Jones" left behind. Report it per type and per source. Use a few hundred synthetic contracts for the estimate and the ten hand-built contracts as the acceptance gate. Say "no misses in N planted items", never "100% recall". Plant hard cases: names that are common words, companies without a suffix, split addresses, signature blocks, homoglyphs and zero-width characters inside names. Gap: no English contract corpus with gold PII labels was found, and the Text Anonymization Benchmark was not checked.

**Leak testing uses three independent guards.** First, a canary scan: give every private field a unique token and assert none of them, nor case-folded or split forms, appear in any request body (captured at the transport), any log line, or the "Copy error details" text. Assert the positive too: the placeholder marker does appear. Second, block sockets suite-wide with `--disable-socket --allow-unix-socket`, which turns "no telemetry" into a property of the whole suite ([pytest-socket](https://github.com/miketheman/pytest-socket)). Its limit is that session-scoped fixtures made before the block can keep access, and native libraries bypass it. Third, a contract test over every step builder that private mode sends exactly `provider: {zdr: true, data_collection: "deny", require_parameters: true}` and no `plugins` or tools. Add a static test that the only host strings in the package are `openrouter.ai` and the GitHub release URL, and a release-level run of the packaged app in a network namespace. Decide whether to send OpenRouter's identifying `HTTP-Referer` header at all ([provider routing](https://openrouter.ai/docs/guides/routing/provider-selection)). Gap: no published way to prove "no telemetry" in a packaged shell exists.

**What OpenRouter privacy settings can and cannot prove.** `zdr: true` follows the account's Safety Retention choice, and self-serve accounts allow Safety Retention by default ([ZDR guide](https://openrouter.ai/docs/guides/features/zdr)). The request flag can only switch enforcement on. From 27 Oct 2026 OpenRouter screens all requests, ZDR included, for child abuse material, and flagged content may be retained. Nothing in the documented response proves a call was ZDR. So the app cannot prove "ZDR only". The best check is to record the provider per call and compare it with the `/api/v1/endpoints/zdr` list, flagging any `safety_retention: true` endpoint ([API reference](https://openrouter.ai/docs/api/api-reference/endpoints/preview-the-impact-of-zdr-on-the-available-endpoints)). Choosing models whose ZDR endpoints are not Safety Retention makes the promise hold either way. That ZDR-list call is a fourth kind of OpenRouter request, so Spec 8.1 must list it. Gaps: whether the endpoint needs a management key, and the error body when no endpoint matches, were not found.

**Prove encryption and deletion by scanning bytes.** After a full fixture review and a forced close, walk the data and temp directories and search every file for the canaries in UTF-8, UTF-16 and case-folded forms. Run it after a clean close and after a simulated crash, so `-wal` and `-journal` files are present. Include a positive control: the same scan on a deliberately unencrypted database must find the canary. Read back the pragmas in a test: `temp_store=2`, `secure_delete` on, `wal_checkpoint(TRUNCATE)` after delete and on close, and `journal_size_limit=0` ([SQLite temp files](https://www.sqlite.org/tempfiles.html), [SQLite pragmas](https://www.sqlite.org/pragma.html)). Test crypto-shredding: copy a review's blob, delete its wrapped key, and assert the blob cannot be decrypted and the key row is gone after a checkpoint. A backup made earlier still holds the old key, and the docs must say so. Inject a hand-written `Clock` for auto-delete and test the boundaries, a backwards jump, a laptop off for months, and a crash between key deletion and row deletion.

**What may honestly be claimed:** "encrypted at rest; once its key is destroyed, unreadable by this app". Do not claim "securely erased" or "forensically unrecoverable", because an app cannot overwrite an SSD block. Tell users to keep full-disk encryption on. Gaps: the notes could not read [NIST SP 800-88 Rev. 2](https://csrc.nist.gov/pubs/sp/800/88/r2/final) text (the cryptographic-erase conditions come from vendor summaries), and whether `secure_delete` acts on WAL frames is untested.

**Injection testing for a no-tools pipeline.** Most public tools target tool-using agents, which this app removes by design. Borrow payload strings and the nine hidden-text PDF fixtures from garak ([commit](https://github.com/NVIDIA/garak/commit/7a605962beea7f0d2e1da816691a2a807d4ac1e6)), and write the suite in pytest. Add the Unicode layer: tag characters, variation selectors, zero-width runs, bidi controls and invisible operators ([garak ASCII smuggling](https://reference.garak.ai/en/stable/ascii_smuggling.html)). Strip the tag block before text reaches the model, but not every zero-width character, because that breaks legitimate joiners ([arXiv 2603.00164](https://arxiv.org/pdf/2603.00164)). Use paired innocent look-alikes so false alarms are measured ([hidden-text-detector](https://github.com/wppoland/hidden-text-detector)). Pass criteria: every hidden-text fixture raises the banner and every look-alike does not; clean and injected labels, numbers and quote spans match, or the injected run degrades only to "unsure"; no injected string or URL reaches any visible field; no clean walk-away becomes anything but walk-away or unsure. Split by cost: keyless replays of "the model obeyed" replies prove code checks still hold, and the paid layer tests whether the model obeys. Gaps: dataset licences (BIPIA, InjecAgent, Tensor Trust) were not read, and garak's own telemetry was not verified.

**Hostile-file defence.** Set limits before parsing and test each one: member count, declared and real expanded size, compression ratio, name safety, page count, time and memory. Python's `zipfile` does not enforce these ([zipfile docs](https://docs.python.org/3/library/zipfile.html)), and declared sizes are attacker-controlled, so cap the real read as well. Parse XML with `resolve_entities=False`, `no_network=True`, `load_dtd=False` and `huge_tree` off ([lxml](https://lxml.de/parsing.html)). The notes judge `defusedxml` too stale to rely on (last release 2021), though the claim about its lxml wrapper being deprecated is from memory. Run each hostile parse in a child process with `resource.setrlimit` and a wall-clock limit. That is also the production design. Use `pytest-timeout` with the thread method for hostile tests ([pytest-timeout](https://github.com/pytest-dev/pytest-timeout)). Use Hypothesis for short every-commit mutation fuzzing and Atheris for a nightly job ([Atheris](https://github.com/google/atheris)). Generate fixtures instead of committing public corpora, whose licences were not confirmed.

**Supply chain, in five steps.** The CI job: `uv sync --locked`; `uv audit --locked`, or `uv export` then `pip-audit` until `uv audit` leaves preview; `licensecheck --zero --only-licenses` on the runtime group; `gitleaks git` over full history; and on release, a CycloneDX SBOM from `uv export`, `actions/attest`, and `SHA256SUMS` ([uv export](https://docs.astral.sh/uv/concepts/projects/export/), [GitHub attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations), [gitleaks](https://github.com/gitleaks/gitleaks)). Add a weekly scheduled audit, because a push-only trigger misses later advisories. Pin Actions by full commit SHA with Dependabot keeping the comments ([GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use)). Gitleaks is in maintenance mode, so expect to revisit it. `pymupdf` (AGPL) fails the licence rule. `pikepdf` (MPL-2.0) needs a decision. The claims allowed are "no known advisories at build time", "licences on the allow-list", and "built by this workflow from this commit". Gaps: the official `uv audit` reference was not read, and sources disagree on its version and flag, so check `uv audit --help` on the pinned version. The Actions "lockfile" and the SLSA level were not verified, so do not quote a level.

**Why pywebview, in plain terms.** The shell choice is decided by who can review the code. Both pywebview and Tauri render through the same system webviews (WebView2 on Windows, WebKitGTK on Linux), so Tauri buys no rendering advantage. Tauri's own docs carry a "Linux Graphics Issues" page, with blank windows on some NVIDIA setups ([Tauri](https://v2.tauri.app/develop/debug/linux-graphics/)), and an open report of a blank window on Fedora 43 with Sway ([issue #15050](https://github.com/tauri-apps/tauri/issues/15050)). pywebview shares that Linux weak point. Tauri's size advantage matters little once a 32 MB to 400 MB NER model is in the bundle. What Tauri has and pywebview lacks is a bundler, capabilities and an updater. pywebview's security guide is two paragraphs and has no capability system. The mitigations are all Python or HTML the developer can read: a strict CSP, `textContent` only, no remote URLs, downloads off, external links to the system browser, devtools off in release, and a narrow `js_api` class ([pywebview API](https://pywebview.flowrl.com/api/)). PyTauri was rejected as young, with seven contributors and a latest release of 2 Sep 2025 as far as the notes could see.

**Two open points to settle.** First, the prototype is multi-page and remembers theme and text size through browser storage, which `file://` may forget. Serving it from pywebview's built-in server on 127.0.0.1 with its per-session token solves that, but adds a listening port. Whether the GTK bridge still uses an internal HTTP server in 6.x was not verified. Document any port and keep it bound to loopback. Second, the CDP debugging port is a listening socket, so it must be impossible to enable in release builds. The `REMOTE_DEBUGGING_PORT` setting defaults to none.

The honest wording the notes propose for local data is worth adopting: contracts and the API key are encrypted at rest and protected from other people who use the computer and from someone who takes the disk, but not from malware running under the user's own account. gnome-keyring says plainly that it cannot keep secrets from other programs in the same session. A Python process also cannot reliably wipe memory, because strings are immutable and libraries copy them.

**Prompts can never be secret.** They leave the machine in plaintext on every call and show in any HTTPS proxy. OWASP says a system prompt "should not be considered a secret" ([OWASP LLM07](https://genai.owasp.org/llmrisk/llm072025-system-prompt-leakage/)). The paid add-on question follows from the same logic. With no server, a licence check runs on the client and can be patched out. Protect any add-on by licence, not obfuscation.

**What v1 should do now so a hosted provider stays possible.** A server is the only place a secret, a paid feature or a real licence check can be protected. It also makes the owner a processor of users' contracts, which weakens the "local-first, no server" claim for those users. This section of the notes is entirely judgement; the research budget was spent before it, and it cites only OWASP and MASVS-based material ([MASVS-RESILIENCE](https://mas.owasp.org/MASVS/11-MASVS-RESILIENCE/)). The seven steps are:

1. Put the AI call behind one provider port whose input is a structured request (task, document excerpt, playbook rule), not a pre-built prompt string. A hosted provider can then build prompts server-side without touching pipeline modules.
2. Keep code-picked labels and quote and number checks on the client, whatever runs the model, so a hosted path keeps the same evidence guarantees.
3. Store credentials under a provider id, so an account token can later sit in the same OS-store slot as the user's own key.
4. Build no client-side licence or feature gating in v1. It would be crackable and set a pattern to undo.
5. Avoid wording that rules out a future opt-in service. Prefer "this version has no server; your contracts go only to the AI provider you choose" over "will never connect to any server".
6. Sign and attest releases from v1, so a future authenticated client starts from a trusted channel.
7. Keep the update check notify-only and opt-in, so a future service cannot quietly become a telemetry channel.

Gaps, stated plainly: GDPR duties for a solo developer running an LLM proxy that handles contracts, upstream zero-retention terms, and the cost of a minimal proxy were not researched. A lawyer is needed before that version is planned.

## Conclusion

Three results change the plan more than the rest. First, a hand-checked, paired design beats clever tooling: the strongest guards here are a human-owned answer table, a canary scan with a positive control, and a socket block across the whole suite, and none needs a new framework. Second, several privacy promises cannot be proven and must be reworded. The app cannot prove OpenRouter ZDR, cannot overwrite an SSD block, and cannot stop same-user malware. A smaller promise that the tests can verify serves non-technical freelancers better than a larger one they cannot. Third, the "defend the code" questions mostly dissolve because the source is public. The money goes to a trade mark, a certificate and attestations, not obfuscation.

The biggest unknowns are measurable, and the first paid run closes most of them. It will show how much cases of the same input correlate, what reasoning tokens cost, whether caching hits, whether each endpoint truly enforces strict schemas, and how often samples disagree. A short list of decisions still needs a person other than the researcher: legal advice on Article 50, the trade mark classes and FSL with proprietary parts; a one-off check of the pywebview licence and of `httpx2`'s maintainer; and a measurement of Presidio latency on a real 60,000-character contract on the developer's machine. The open choices in Spec section 13 (the shell, how Presidio is bundled, which models) should still go to the user as questions. This report gives a recommendation for each and the evidence behind it, but does not settle them.
